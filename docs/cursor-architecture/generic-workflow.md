## 1. 适用范围与定位

**适用于**：`task_type ∈ { code, research, generic }` 且未命中更专 flow。  
**不适用于**：`prd`、`quick_answer`、以及任何已明确命中专 flow 的任务。

Generic Workflow v1.2 的定位是：

- 提供稳定的通用任务推进节奏（Phase 0～4）
- 保障最小可验证交付
- 保持与规则层、派发层、风险门禁的清晰边界

它不负责：

- 取代入口定向层的主路径判定职责
- 取代规则层（澄清、事实准确、效率、纠错等）
- 承担 PRD 主流程
- 在本 flow 内重写风险治理本体（由 `risky-change-gate` 负责）

---

## 2. 核心硬规则（执行时必须满足）

1. **专 flow 优先**：命中专 flow 时，Generic 不接管。  
2. **主代理唯一写入**：最终决策、最终写入、最终交付只由主代理完成。  
3. **先证据，后判断**：关键事实必须有工具或上下文证据支撑。  
4. **未验证，不宣称完成**：任何“完成”表述必须附验证事实或边界说明。  
5. **高风险必接门禁**：命中高风险条件时必须接入 `risky-change-gate`。  
6. **无新证据，不重复修复**：禁止机械重试同一路径。  
7. **受阻先收敛**：无法继续推进时，回退阶段或请求确认，不无限硬扛。
8. **上下文要可恢复**：Phase 0 先加载上下文，Phase 4 后写回索引与状态（`context-governance`）。

---

## 3. 执行流程（Phase 0～4）

## Phase 0 — 定性

目标：先判断任务，再决定推进强度。

### 0.1 明确目标

识别任务要完成什么、约束是什么、最终产出是什么。

### 0.2 判断主导类型

在以下四类中选一个：

- `code`
- `research`
- `hybrid`
- `other`

说明：

- `code`：以代码/配置/测试改动为主
- `research`：以检索、比对、分析结论为主
- `hybrid`：研究结论显著影响实现路径，且最终要落地仓库改动
- `other`：非 PRD 且不由前三类主导的通用任务

### 0.2.1 `hybrid` 最小闭环（Phase 0 内必答）

当选定主导类型为 `hybrid` 时，在离开 Phase 0 前必须在回复中显式写出（可用简短列表）：

1. **研究侧产出物**：计划落盘的笔记/结论文档路径；若仅对话内交付，须写明原因。  
2. **实现前闸口**：哪一条研究结论未落实前禁止开始代码改动；若无闸口，须写「无闸口」并说明依据。  
3. **顺序声明**：默认「研究 → 实现」；若与用户指定顺序相反，须引用用户原话作为依据。

未满足以上三点不得进入 Phase 1。

### 0.3 判断复杂度（硬锚）

判定信号：

- 文件数（1 / 2～5 / >5）
- 目录跨度（单目录 / 2～3 目录 / 跨模块）
- 是否需策略确认（无 / 1 处 / 多处）
- 是否不可逆（否 / 可回滚 / 不可逆）
- 是否需并行调查（否 / 可选 / 通常需要）
- 是否需先外部调研（否 / 轻量 / 结构化）
- 是否命中门禁（否 / 否 / 是）

**分级规则**：

- 命中 ≥3 个“偏复杂”信号 → **复杂**
- 命中 ≥2 个“偏中等”且无“偏复杂” → **中等**
- 其余 → **简单**

### 0.4 判断是否转交或接门禁

- 任务本质应由专 flow 处理 → 停止当前 flow 并提示切换
- 命中高风险条件 → 标记并接入门禁流程

> **上下文前置动作**：进入 Phase 0 前先调用 `context-governance` 的 Load，恢复活跃任务、决策与产物索引。

---

## Phase 1 — 收集上下文

目标：获取最小充分证据，避免盲动。

### 1.1 `code`

优先收集：代码位置、调用链、配置入口、相关测试、既有模式。

### 1.2 `research`

优先收集：来源、事实、版本、差异点、结论缺口。

### 1.3 `other`

优先收集：相关文档、现有结构、上下文约束、既有格式约定。

### 1.4 `hybrid`

默认先收敛研究结论，再进入实现；若用户明确指定反序，可按指定执行。

### 1.5 Subagent 原则

可用于：广搜、并行只读调查、多路径初筛。  
不可用于：最终写入、最终裁决、最终交付。

---

## Phase 2 — 方案

目标：只在必要时做方案，不让所有任务都进入重计划。

### 2.1 简单

可跳过正式方案；内部最小执行提纲即可。

### 2.2 中等

至少明确：主要步骤、影响范围、验证方式。

### 2.3 复杂

必须先对齐方案再执行，至少包含：

- 边界
- 路径
- 影响面
- 验证方式
- 回退思路

复杂任务推荐进入 Plan，再回 Agent 执行。

### 2.4 执行前最小进入条件

在进入大规模实现、修复或 dry run 前，必须至少明确：

- 本轮交付物类型
- 目标文件或目标目录
- 验证命令或验证方法
- 风险等级
- 是否需要 `risky-change-gate`

若上述 5 项任一缺失，不得进入大规模改动。

默认动作：

- 目标不清 -> 回到 Phase 0 继续定向
- 风险不清 -> 先做风险分级
- 验证不清 -> 先写验证方案

---

## Phase 3 — 执行

目标：最小可证明切片推进，并持续验证。

### 3.1 执行原则

- 主代理唯一写入
- 先做最小证明切片
- 每完成关键切片至少验证一次
- 优先依据真实输出调试
- 不得无证据猜因

### 3.2 连续失败收敛

1. 检查是否有新证据
2. 无新证据则停止重复修复
3. 回退 Phase 1 补上下文，或回到 Phase 2 重收敛方案
4. 若已变为边界/策略问题，请求确认

---

## Phase 4 — 验证与交付

目标：确认结果可信，并留下最小完整交付。

### 4.1 最低验证要求

**`code` / `hybrid`（代码侧）**：至少执行与改动最相关验证（测试、lint/typecheck、命令、冒烟其一或组合）。

**`research` / `hybrid`（研究侧）**：至少完成来源核对、结论自检、不确定项标注。

**`other`**：至少完成格式一致性、路径/链接有效性、步骤可执行性走查、范围完整性核对。

### 4.2 标准交付物（固定模板）

1. **验证摘要**：做了什么验证，结果如何；若未验证，必须说明原因。  
2. **落盘列表**：修改了哪些文件；若无文件变更写“无文件变更”。  
3. **局限与后续**：已知限制、未覆盖点、待确认点、建议下一步。

> **交付后动作**：固定模板输出后，执行 `context-governance` Write-back，更新 `active-workstreams.md`；若新增关键产物/决策，同步更新 `artifact-index.md` 与 `decision-log.md`。

---

## 5. `hybrid` 触发与降级规则（硬锚）

进入 `hybrid` 必须同时满足：

1. 研究结论会显著改变实现路径（非查 1～2 个 API 即可）
2. 最终需要仓库改动
3. 研究与实现两侧工作量都达到“中等”及以上

不满足任一条件，降级为 `code` 或 `research`。

---

## 6. 风险门禁接入点（硬锚）

命中高风险时，按下列固定接入点执行：

- **Phase 0**：完成触发识别并标记“必须门禁”
- **Phase 2**：执行门禁 Phase A/B（B 未完成不得进破坏性实施）
- **Phase 3**：执行门禁 Phase C（逐步追踪）
- **Phase 4**：执行门禁 Phase D（验证矩阵作为完成前置）

### 6.1 Reviewer 最小门槛

以下情况默认需要 reviewer：

- 高风险执行完成但仍需独立核验
- 架构或治理口径变更
- 复杂 `hybrid` 任务已形成正式结论并将影响后续实施

以下情况可不派 reviewer：

- 单文件、低风险、且验证清晰的小修复
- 纯研究笔记且不做正式对外结论

---

## 7. 失败与停机机制

### 7.1 必须停下的情况

- 连续尝试且无新证据
- 执行问题变成边界问题
- 路径选择显著影响结果但缺少确认
- 当前上下文不足以可靠推进
- 已进入高风险场景但未过门禁

### 7.2 停机后最小输出

- 已确认事实
- 当前阻塞点
- 已尝试路径
- 下一步可选方案

---

## 8. 持久化原则（轻量但可审计）

### 8.1 必须落盘

- 代码/配置/测试改动
- 正式文档交付
- 用户要求保留的最终研究产物

### 8.2 视情况落盘

- 中间扫描结论
- 临时研究笔记
- 草图方案
- 临时排障记录

### 8.3 团队共识线（新增硬锚）

凡会影响**后续接手、回滚判断、风险复盘**的中间结论，必须落盘；其余按复用价值决定。

---

## 8.1 上下文治理接入（共享能力）

Generic flow 使用共享技能 `context-governance` 管理跨会话上下文：

| 时点 | 动作 | 目标文件 |
|------|------|----------|
| Phase 0 前 | 加载上下文（Load） | `context/active-workstreams.md`、`context/decision-log.md`、`context/artifact-index.md` |
| Phase 2 后（复杂任务） | 更新阶段与下一步 | `context/active-workstreams.md` |
| Phase 4 后 | 写回产物与决策（Write-back） | `context/active-workstreams.md`、`context/artifact-index.md`、`context/decision-log.md` |

冲突规则：上下文记录与用户当轮新指令冲突时，以用户当轮指令优先，并在决策日志记录覆盖说明。

---

## 9. 与其他层的边界

- 与入口定向层：入口定向负责主路径判定；Generic 仅做误入识别与切换提示。
- 与 PRD Workflow：Generic 不承担 PRD 主交付。
- 与规则层：Generic 不替代 `.mdc` 的全局约束。
- 与风险门禁：Generic 负责识别与接入，治理本体由 `risky-change-gate` 执行。
- 与 Workflow 演进策略：`code` / `research` 何时从 Generic 中正式迁出，受 `docs/cursor-architecture/workflow-evolution-policy.md` 约束；在入口定向口径未按该政策更新前，Generic 继续承接这三类任务。

---

## 10. 一句话执行口径

当没有更专门 flow 接管时：  
**先定性，再补证据；必要时做最小方案；主代理分步执行并验证；最后按统一结构交付。**

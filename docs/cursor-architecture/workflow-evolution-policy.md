# Workflow Evolution Policy v1.0

> 创建日期：2026-04-11  
> 状态：v1.0（已验收并纳入治理台账）  
> 角色：Workflow Evolution Agent  
> 作用：定义何时应从 `generic-workflow` 拆出专 flow、如何推进拆分、何时允许更新当前入口定向口径。

---

## 1. 目标与适用范围

本文件用于约束 Cursor 原生任务编排架构在后续版本中的 Workflow 演进，避免出现以下失控情况：

- 为了“看起来更完整”而过早新增 flow
- 入口定向口径频繁变动，导致入口不稳定
- Generic 承担过多差异化任务，但没有明确退出机制
- 新增专 flow 后与既有 `generic-workflow` 职责重叠

本文件只回答四类问题：

1. **什么时候该拆** `code-workflow`、`research-workflow` 等专 flow  
2. **什么时候不该拆**  
3. **拆分应经过哪些阶段**  
4. **什么时候允许更新入口定向口径**

本文件**不负责**：

- 改写现有 `generic-workflow`、`prd-workflow` 细节
- 定义入口定向验收样本
- 定义 `context/*` 文件 schema
- 替代 `risky-change-gate` 的风险治理职责

---

## 1.1 权威性与引用关系

本文件在“Workflow 演进治理”问题上的定位是**权威规则文档**，其关系如下：

- `README.md`：负责登记架构模块与版本状态；不重复展开演进准则细节
- `README.md` 中的入口定向口径：负责当前主路由说明；是否允许把候选 flow 提升为正式主路径，受本文件约束
- `generic-workflow.md`：负责当前通用执行流；何时收缩某类 lane 的说明，受本文件约束

换句话说：

- **README 是目录**
- **README 中的入口定向口径是当前入口实现说明**
- **Generic Workflow 是当前兜底执行实现**
- **本文件是专 flow 晋升与迁移的治理准则**

若四者描述出现冲突，按以下顺序解释：

1. 当前运行中的主路径口径，以 `README.md` 的入口定向描述为准  
2. 是否允许改主路径口径、何时改，以本文件为准  
3. 模块登记与版本展示，以 `README.md` 为准  
4. 当前兜底执行细节，以 `generic-workflow.md` 为准  

---

## 1.2 生效口径

本文件自纳入 `docs/cursor-architecture/` 后立即生效，但其生效范围仅限于：

- 新增专 flow 的评审
- 候选 flow 的阶段判定
- 入口定向口径是否可更新的门槛判断
- 新旧 flow 兼容迁移与回退

本文件**不直接触发**任何路由切换。  
在满足 Stage 3 之前，`code` / `research` / `generic` 仍按当前入口定向口径进入 `generic-workflow`。

---

## 2. 当前架构基线

当前 v1 的执行现实是：

- `prd` 已有专 flow
- `quick_answer` 直接回答
- `code`、`research`、`generic` 三类仍统一进入 `generic-workflow`
- `generic-workflow` 内部通过 `primary_lane` 再做细分

因此，后续演进的默认原则不是“继续堆新 flow”，而是：

**先让 Generic 稳定承接，观察稳定分化信号，再决定是否把某类任务提升为专 flow。**

---

## 3. 演进原则

### 3.1 入口稳定优先于内部完美

如果拆分会显著增加入口定向复杂度，但对交付质量提升有限，则优先保持现状。

### 3.2 先有稳定差异，再有专 flow

只有当某类任务在目标、阶段、验证、工具或风险模型上持续表现出稳定差异，才值得拆分。

### 3.3 先沉淀规则，再抽成 flow

若差异仅体现在少量补充规则、附加检查表或 Phase 内分支，不应直接拆独立 flow。

### 3.4 Generic 是默认兜底，不是失败品

`generic-workflow` 的存在价值是承接未成熟类别、低频类别和混合任务。拆分的目标不是替代 Generic，而是降低 Generic 的认知负担。

### 3.5 入口定向口径更新必须滞后于 flow 成熟

先有稳定设计文档、稳定技能、稳定验收样本，再调整入口定向口径。禁止只因为“计划要拆”就提前改主路径。

---

## 4. 拆分判定模型

判断某类任务是否应从 `generic-workflow` 中拆出，统一使用六类信号。

### 4.1 六类信号

| 信号 | 说明 | 是否关键 |
|------|------|----------|
| 任务量稳定出现 | 在真实任务中重复出现，不是一次性需求 | 是 |
| 阶段结构显著不同 | 相比 Generic，需要稳定新增或改写多个阶段动作 | 是 |
| 验证模型显著不同 | 验证方式不是 Generic 的轻度变体，而是独立模型 | 是 |
| 风险/工具画像不同 | 常用工具、门禁条件、外部依赖明显不同 | 否 |
| 交付物形态不同 | 输出模板、产物形态、完成标准长期不同 | 否 |
| Generic 内部成本过高 | 在 Generic 中持续依赖大量 `if/else` 或解释负担 | 是 |

### 4.2 推荐拆分阈值

满足以下条件时，进入“可拆分候选”：

1. 命中 **至少 4/6** 个信号
2. 其中必须包含：
   - `任务量稳定出现`
   - `阶段结构显著不同`
   - `Generic 内部成本过高`

若只命中 2～3 个信号，优先在 `generic-workflow` 内做附录、lane 强化或检查表补强，不直接拆 flow。

---

## 5. 明确不拆的情况

以下情况禁止作为拆 flow 理由：

- 只是任务名称看起来不同
- 只是输出格式不同，但执行路径几乎相同
- 只是某一周任务突然增多
- 只是某类任务更重要，但流程并未显著不同
- 只是希望“架构图更完整”
- 只是为了配合组织分工，而非执行差异

一句话判断：

**如果差异主要发生在“内容主题”，而不是“执行机制”，就不该拆。**

---

## 6. 拆分生命周期

所有专 flow 的诞生统一经过四阶段，不允许跳级。

### Stage 0 — 观察期

状态特征：

- 仍由 `generic-workflow` 承接
- 只在 Generic 内通过 `primary_lane`、附加检查点或补充说明应对
- 开始收集该类任务的样本、痛点和失败模式

阶段出口：

- 已出现足够多的重复任务样本
- 差异不是偶发，而是稳定模式

### Stage 1 — 候选期

状态特征：

- 形成候选 flow 名称，如 `code-workflow`、`research-workflow`
- 先有独立设计文档，但入口定向口径尚不更新
- 真实执行仍以 Generic 为主，候选文档只用于架构评审或灰度试运行

阶段出口：

- 已形成独立的阶段设计
- 与 Generic 的边界说得清楚
- 已有初步验收样本

### Stage 2 — 试运行期

状态特征：

- 候选 flow 已有 `SKILL.md`
- 仅在明确命中、且架构批准的前提下灰度使用
- 入口定向仍保守，必要时可通过人工选择进入候选 flow

阶段出口：

- 试运行结果稳定
- 与 Generic 的回退机制清晰
- 没有出现大规模误路由或边界冲突

### Stage 3 — 正式晋升

状态特征：

- 设计文档、技能、验收样本全部齐备
- 入口定向口径更新，正式纳入主路径
- Generic 保留兜底与兼容职责

阶段出口：

- 新 flow 在一段观察窗口内表现稳定
- Generic 中与该类别有关的说明可收缩为边界提示

---

## 7. 入口定向口径更新策略

入口定向口径的更新门槛必须高于“文档已写完”。

### 7.1 更新前置条件

允许将新 flow 写入当前入口定向口径之前，必须同时满足：

1. 已有独立设计文档  
2. 已有独立 `SKILL.md`  
3. 已完成一轮试运行  
4. 已有可复用的路由样本与验证记录  
5. 已定义误路由后的回退策略  

缺一项都不进入正式主路径。

### 7.1.a 与当前入口定向口径的映射

当前入口定向口径中，`code`、`research`、`generic` 仍统一指向 `generic-workflow`。这在本政策下是**正确且应保持**的默认状态。

只有当候选 flow 满足本文件 **Stage 3 + §7.1 全部前置条件** 后，才允许将：

- `code` 的目标列从 `generic-workflow` 改为 `code-workflow`
- `research` 的目标列从 `generic-workflow` 改为 `research-workflow`

在此之前，即使候选文档或候选技能已存在，入口定向口径也不得提前改写。

### 7.2 更新原则

- 一次只提升一个新 flow，避免多点同时变更
- 保留 `generic-workflow` 作为兜底
- 更新入口定向口径时，同步更新架构总览和边界说明
- 不在同一轮里同时重写分类标准与 flow 边界

### 7.3 回退原则

如果新 flow 在试运行后出现以下情况，应回退到 Generic：

- 误路由率高
- 与 Generic 的边界无法稳定说明
- 用户输入难以被可靠识别
- 实际任务量不足以支撑独立维护

---

## 8. 与 Generic 的兼容关系

新增专 flow 后，`generic-workflow` 仍保留三项职责：

1. 承接所有未命中专 flow 的任务
2. 承接混合、模糊、低频任务
3. 在新 flow 失效或被回退时继续兜底

因此，拆分后的正确结构不是“Generic 被掏空”，而是：

- Generic 负责广谱承接
- 专 flow 负责高频、高差异、高稳定性的任务类型

---

## 8.1 新旧 Flow 兼容迁移策略

当某个候选 flow 从 Stage 2 进入 Stage 3 时，迁移必须满足“**先并存、再收缩、后稳定**”，禁止一步到位替换。

### 迁移原则

1. **先保留 Generic 兜底**  
   新 flow 晋升后，`generic-workflow` 不立即删除对应说明，只把其降级为“边界提示 + 回退入口”。

2. **先迁路由，再迁说明**  
   优先更新入口定向口径的命中条件与回退条件；待观察窗口结束后，再收缩 Generic 内对该类别的细节说明。

3. **先兼容旧任务，再优化新任务**  
   已存在的模糊输入、混合输入、低置信度输入，仍默认允许回退到 Generic，不强制命中新 flow。

4. **迁移失败可整类回退**  
   若新 flow 在观察窗口内表现不稳定，应允许整类任务回退到 Generic，而不是继续硬顶。

### 迁移步骤

| 步骤 | 动作 | 责任边界 |
|------|------|----------|
| Step 1 | 新 flow 进入灰度可用状态，保留 Generic 原有承接能力 | Workflow owner |
| Step 2 | 入口定向口径增加精确命中条件，并保留 Generic 兜底 | Architecture Owner |
| Step 3 | 收集误路由、回退、边界冲突样本 | Routing / QA |
| Step 4 | 观察窗口结束后，压缩 Generic 中对应类别的说明为边界条款 | Workflow owner |
| Step 5 | 若稳定，则形成正式主路由；若不稳，整类回退到 Generic | Architecture owner |

### 观察窗口建议

- 至少覆盖一轮真实任务样本，而不是只看静态用例
- 至少出现一次“模糊输入”与一次“混合输入”场景
- 至少验证一次从专 flow 回退到 Generic 的完整路径

### Generic 中应保留的最小兼容内容

即使某类任务已经拆出专 flow，`generic-workflow` 中仍应保留：

- 误路由识别语句
- 回退触发条件
- 对应专 flow 的跳转说明
- 对低置信度输入的兜底处理

## 9. 近期候选 flow 判断

基于当前 v1 文档现状，近期只建议观察两个候选：

### 9.1 `code-workflow`

可能具备拆分价值的原因：

- 代码类任务量通常较高
- 验证模型更强依赖测试、lint、构建、运行输出
- 失败修复路径比研究类更强闭环

当前不建议立即晋升的原因：

- 还缺路由基准与真实样本矩阵
- 还没证明 Generic 内的 `code` lane 已经复杂到必须剥离

### 9.2 `research-workflow`

可能具备拆分价值的原因：

- 来源质量、引用、结论约束与代码类不同
- 交付形态常是报告、比较、结论与局限说明

当前不建议立即晋升的原因：

- 研究类任务边界容易与 `generic`、`prd` 交叉
- 还需要通过样本确认其阶段结构是否已稳定独立

### 9.3 当前结论

当前阶段的正确动作是：

- **先补验证资产**
- **先补 context schema**
- **继续让 `code` / `research` 留在 Generic 内观察**

而不是立刻新增 `code-workflow` 或 `research-workflow`。

## 10. 版本演进触发点

当以下任一事件发生，应评估是否升级本政策版本：

- 新增一个候选专 flow
- 入口定向标准发生结构性变化
- Generic 的 `primary_lane` 分类模型发生变化
- 风险门禁或上下文治理显著影响 flow 边界

建议版本口径：

- `v0.x`：策略草案期
- `v1.0`：至少完成一轮真实试运行验证后
- `v1.x`：在不推翻框架前提下微调阈值和流程

### 当前版本判定

本次升级到 `v1.0` 的依据不是“专 flow 已落地”，而是：

- 演进原则已冻结
- 拆分阈值已冻结
- 入口定向更新门槛已冻结
- Generic 兼容迁移策略已冻结
- 回退条件已冻结

因此，`v1.0` 表示“**治理规则可验收**”，不表示“`code-workflow` / `research-workflow` 已可上线”。

## 10.1 Agent 3 交付闭环与正式关闭条件

Agent 3 的职责边界只覆盖“Workflow 演进治理规则”本体，不覆盖 Context Governance 的索引同步。因此本交付需要区分：

### A. Agent 3 内容完成条件

满足以下条件，即可判定 Agent 3 **内容完成**：

1. 本文件已定义拆分阈值  
2. 本文件已定义入口定向口径更新门槛  
3. 本文件已定义新旧 flow 兼容迁移与回退  
4. `README.md` 已登记本文件的模块地位与版本  
5. `generic-workflow.md` 与 `README.md` 已补足对本文件的显式引用  

### B. 正式关闭条件

满足以下条件，才能判定 Agent 3 **正式关闭**：

1. Agent 3 的内容完成条件全部满足  
2. Governance owner 已在 `artifact-index.md` 中登记本文件  
3. Governance owner 已在 `active-workstreams.md` 中同步 Agent 3 状态变化  
4. 如本轮策略引起架构状态变化，相关 `decision-log.md` 已按治理规则记录  

### C. 责任边界

- Agent 3 负责：规则文档本体、显式引用关系、版本与生效口径
- Agent 2 负责：`artifact-index.md`、`active-workstreams.md`、`decision-log.md` 等治理台账同步

因此，若内容已完成但治理台账未收口，正确状态应表述为：

**“Agent 3 内容已完成并可验收，正式关闭待治理层收口。”**

## 11. 架构师验收清单

评审这份策略时，只看五个问题：

1. 有没有把“主题差异”误判成“执行差异”  
2. 有没有为了完整性而过早拆 flow  
3. 入口定向口径更新门槛是否足够保守  
4. Generic 是否仍保持兜底能力  
5. 新 flow 的回退机制是否明确  

若其中任一问题答不清，则该候选 flow 不应晋升。

---

## 12. 一句话口径

**先让 Generic 承接并暴露稳定分化，再把真正高频、强差异、可验证的类别晋升为专 flow；入口定向口径永远最后改。**

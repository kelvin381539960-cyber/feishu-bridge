# AIX 用户注册（开户与 KYC）PRD

## 1. 背景

AIX Phase 2 MVP 将「开户与身份认证」作为用户进入资金与卡片能力的前置门槛（E1）。业界「注册」常被理解为创建登录身份；在本产品中，**可对外承诺的「注册完成」**应与 **KYC 审核通过与核心账户开立** 对齐，避免合规与期望落差（I1）。

本 PRD 读者：**移动端与后端研发、测试、产品、合规/风控**。成功标准：各角色能据本文达成范围共识，并按验收标准设计用例与联调计划。

## 2. 目标与指标

### 2.1 业务目标

- 用户可在 AIX App 内完成开户申请与身份核验所需资料提交，并获知明确结果（通过 / 拒绝 / 待补充）。
- 审核通过后，用户在平台侧具备与 MVP 一致的基础账户能力（与账本开立联动）（E2）。

### 2.2 关键指标（建议，可在立项时取值）

| 指标 | 说明 | 备注 |
|------|------|------|
| 开户漏斗完成率 | 发起 → 提交成功 → 审核通过 | 分渠道/国别观察 |
| 审核时效 | 从提交到终态通知的 P50/P95 | 依赖 KUN/AAI SLA（G1） |
| 一次通过率 | 首次提交即通过 / 需补件比例 | 驱动 OCR/活体体验优化 |
| 失败可解释率 | 拒绝/补件原因可被用户理解且可行动 | 文案与错误码映射 |

## 3. 范围与非目标

### 3.1 范围内（MVP）

- 护照 **OCR** 采集与信息回填（E1）。
- **活体检测 + 人脸比对**（E1）。
- **地址证明（POA）** 上传与核验结论回传（E1）。
- 与 Flow 1 一致的系统协作：App 提交审核请求 → Platform 编排并向 KUN 发起身份核验 → 采集侧与 AAI/KUN 交互 → 审核结果回传 → 通过后联动 **Ledger** 开立用户账户 → App 结果展示（E2）。

### 3.2 非目标（本 PRD 不包含）

- 卡片申请与发卡、链上充提、Swap、Yield 等产品流程（见 MVP 其他章节）（E1）。
- 具体营销增长策略（邀请码、渠道归因等）：如需，另起 PRD。
- KUN/AAI 内部评分模型与规则细节：以合作方与合规约定为准（G1）。

## 4. 用户与场景

| 角色 | 描述 |
|------|------|
| 新用户 | 首次安装 App，希望完成注册并开通账户能力 |
| 存量未开户用户 | 已登录但未完成 KYC，需补全流程 |
| 合规审查方 | 关注敏感数据路径、可审计性与数据留存策略（与 G1、开放问题联动） |

**核心场景**：用户在稳定网络环境下，按引导完成护照 OCR、活体、POA 提交；提交后出现「处理中」；收到终态后可进入 MVP 允许的后续功能。

## 5. 用户故事

1. **作为** 新用户，**我希望** 用护照快速填入基本信息，**以便** 减少手写错误与退件。
2. **作为** 新用户，**我希望** 活体与人脸步骤清晰、可重试，**以便** 在光线不佳时仍能完成验证。
3. **作为** 新用户，**我希望** 上传 POA 并看到「已收到/处理中/需补件」等状态，**以便** 知道下一步该做什么。
4. **作为** 合规利益相关方，**我希望** 敏感采集与传输路径可说明、可审计，**以便** 满足监管与合作方要求。

## 6. 功能需求

### 6.1 流程与状态

| ID | 需求描述 | 优先级 |
|----|----------|--------|
| FR-01 | App 提供开户入口；未通过 KYC 的用户访问受控功能时应被引导至开户流程 | P0 |
| FR-02 | 用户可完成护照 OCR；支持在 OCR 结果上人工校正（若业务允许） | P0 |
| FR-03 | 用户可完成活体与人脸比对流程；失败时给出可行动提示与重试策略（在合作方允许次数内） | P0 |
| FR-04 | 用户可上传 POA；展示文件格式/大小等约束 | P0 |
| FR-05 | 用户可「提交审核」；提交后展示处理中状态，并支持后续打开 App 恢复进度（依赖 A1：需有稳定会话/用户标识策略） | P0 |
| FR-06 | 收到终态（通过/拒绝/补件）后，App 以明确文案与下一步 CTA 呈现；**通过**后与 Ledger 开立账户一致（E2） | P0 |
| FR-07 | 拒绝与补件场景：展示原因类别（在 KUN/AAI 返回信息允许范围内），避免泄露内部风控细节 | P1 |

### 6.2 平台与编排（对研发可见）

| ID | 需求描述 | 优先级 |
|----|----------|--------|
| FR-10 | Platform 能向 KUN 发起身份核验请求，并关联单次开户会话 | P0 |
| FR-11 | 异步接收 KUN 审核结果；状态机具备终态与超时处理（具体时限 G1） | P0 |
| FR-12 | 审核通过后，触发与 Ledger 的开户联动，并保证与通知用户顺序上的业务一致性（避免「通知成功但未开户」可感知窗口过长） | P0 |

### 6.3 安全与隐私（摘要级）

| ID | 需求描述 | 优先级 |
|----|----------|--------|
| FR-20 | 传输与存储遵循项目安全基线；敏感字段最小化展示 | P0 |
| FR-21 | 日志中不得记录完整证件影像与完整证件号明文 | P0 |

## 7. 关键流程（与 Flow 1 对齐）

以下步骤与概要设计 Flow 1 一致（E2）：

1. 用户发起开户申请（App）。
2. App 向 Platform 提交开户审核请求。
3. Platform 向 KUN 请求身份核验服务。
4. App 采集并上传证件、人脸、地址证明至 **AAI**（路径细节见开放问题：历史文档曾强调不经 Platform 后台，当前结构图仍以 App→AAI 为主）（E2）（E4）。
5. AAI 将采集结果回传 KUN。
6. KUN 将审核结果通知 Platform。
7. 审核通过后，Platform 联动 **Ledger** 开立用户账户（E2）。
8. Platform 将开户结果通知 App，用户可见终态。

## 8. 非功能需求

| 类别 | 要求 |
|------|------|
| 可用性 | 弱网可恢复；关键步骤离线阻断与提示 |
| 性能 | OCR/活体页面响应可接受；提交后状态查询频率合理，避免打爆接口（G1） |
| 国际化 | 文案与日期/地址格式预留；MVP 若单语种可先标注技术债 |
| 可观测性 | 开户漏斗埋点与错误码统计；支持问题定位但不记录敏感明文（FR-21） |

## 9. 数据与权限（摘要）

- **身份数据**：护照信息、活体/人脸、POA 文件及元数据；分级存储与保留周期遵循合规结论（G1）。
- **权限**：仅开户相关服务可写；审核人员（若有）访问路径与审批单独定义，不在本 PRD 展开。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 第三方 SLA 不稳定 | 处理中状态过长、投诉上升 | 超时策略与用户安抚文案；与 KUN 约定回调与查询（G1） |
| OCR/活体误杀 | 一次通过率低 | 可行动错误提示、有限次重试、人工工单通道（运营策略另案） |
| 多版本架构叙事并存 | 研发实现与合规说明不一致 | 以当前 `05-money-flows.md` 为单一对外主链，历史差异清理排期（E4） |

## 12. 验收标准

1. **Happy path**：新用户可完成 OCR + 活体 + POA 并提交；在测试环境模拟 KUN「通过」回调后，用户收到成功结果，且后台可验证 **Ledger 侧账户已开立**（或与测试替身等价的断言）（E2）。
2. **拒绝 path**：模拟「拒绝」回调，App 展示拒绝终态与合规范围内原因，不产生资金类副作用。
3. **补件 path**（若 KUN/AAI 支持）：可重新进入补件流程直至终态。
4. **安全**：抽样检查客户端与服务器日志，无 FR-21 禁止内容。
5. **恢复**：杀进程或断网后重新打开，用户可回到上次未完成步骤或看到明确状态（依赖 A1 实现选型）。

## 13. 里程碑（建议）

| 阶段 | 交付物 |
|------|--------|
| M1 | 与 KUN/AAI 对齐字段与回调；状态机草案通过评审（G1） |
| M2 | App 三合一采集流程联调通过（沙箱） |
| M3 | 与 Ledger 开户联动与终态通知联调通过 |
| M4 | 埋点与验收用例全绿；准备上线检查清单 |

## 14. 开放问题

1. **敏感数据路径**：是否强制「不经 Platform 后台直传 AAI」为硬约束；若与当前主叙事图示存在出入，需架构与合规书面裁定（E4）。
2. **KYC 前用户标识**：匿名设备 → 登录账号 → KYC 会话的绑定关系与合并策略（A1）。
3. **国别与证件类型扩展**：MVP 仅护照的前提下，POA 语言/格式清单由谁维护（G1）。
